## Current state

The phase-0 result is met on the local stack (605 tests, 2026-08-19): real
sessions via Supabase-managed auth (GoTrue signups mirror into
`public.users` via a trigger), workspace create/rename/delete with the
activity feed reading events back, project wizard + settings, and codebase
scans that save and load back into the import screen. `NEXT_PUBLIC_AUTH_ENABLED=true`
is set in `.env.local`, so route guards and session validation are live.
Not built yet: a created project does not appear in any list, and the
rescan-diff against the saved snapshot is not wired. Remaining: cloud
Supabase project, production email sender, projects-list read path, CI,
deploy (docs/blocker.md).

Read `docs/phase.md` before starting anything; it says exactly where each phase
stands and what is blocked.

## Working rules

1. **Build only what is explicitly requested.** The project owner directs every
   step. Never scaffold ahead, never anticipate the next feature, never add a
   dependency that was not asked for.
2. **Follow the build order** in `docs/04-roadmap.md`. Do not work ahead of the
   current step.
3. **Follow the 18-step feature workflow** in `docs/05-feature-workflow.md`.
   Requirement → user flow → UI/UX → database → API come before any component
   file. Nothing is DONE without tests, docs, and monitoring.
4. **Apply the scope test.** Every feature must serve a layer —
   Understand, Guide, or Execute — and, during v1, a link in the MVP chain. If
   it serves neither, it does not belong.
5. **Keep the trackers current — this is not optional.**
   - `docs/phase.md` — flip an item's status the moment it changes (⬜ → 🟡 when
     you start, 🟡 → ✅ only after its gates pass), tick 18-step rows as they
     complete. When a new phase is specified, add it in the same shape: scope,
     flow diagram, per-item checklist, gate, blockers.
   - `docs/06-status.md` — mirror anything that finished.
   - `docs/blocker.md` — add a blocker the moment one appears, move it to
     Resolved only when it actually clears, and record any new external service
     or credential the work turns out to need.
   - `docs/bug.md` — log every defect: symptom, root cause, fix, how it was
     caught, and what stops it recurring. Including bugs you introduced and
     fixed in the same turn; especially anything that failed silently.

   Never report work as done without updating what changed. A **Stop hook**
   (`.claude/hooks/check-trackers.sh`) enforces this: it blocks the turn when
   `src/` changed but no tracker did. It does not fire twice in a row, so a
   genuinely tracker-free change (a formatting pass, a revert) can be explained
   and stopped again.

## Commands

```bash
npm run dev         # dev server, http://localhost:3000
npm run build       # production build
npm run typecheck   # tsc --noEmit
npm run lint        # eslint
npm run format      # prettier --write .
npm test            # vitest, run once
```

`typecheck`, `lint`, `test`, and `build` must all pass before any step is
called done.

## Conventions

- Import through the `@/*` alias.
- Read env vars via `@/lib/env`, never `process.env` directly.
- Feature code lives in `src/features/<name>/` and is imported through that
  feature's `index.ts`. Features never import each other.
- `src/components/ui/**` is generated by the shadcn CLI — do not hand-edit.
  Add components with `npx shadcn@latest add <name>`.
- Server-only code (crypto, hashing, cookies, database) is exported from a
  feature's `server.ts`, never its `index.ts` — the barrel is reachable from
  client components. Server modules import `server-only` so a mistaken client
  import fails the build. See `src/features/auth/`.
- Write the test first, watch it fail, then implement. Security and business
  logic get tests; a passing test that was never seen to fail proves nothing.
