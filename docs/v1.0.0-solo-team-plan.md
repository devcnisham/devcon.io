# DevCon v1.0.0 — Academic Track (Solo / Team)

> **v1.0.0 = the first shippable release**, targeting **students building college projects or personal projects**.
> Covers **both** solo and group projects. Build order inside the release: **solo first, then team.**
>
> **Supersedes:** the parent plan sequences the *competition* track first. This release targets academic instead. The parent plan is deliberately left unchanged as the record of that earlier reasoning — this note is the reconciliation.
> Parent plan: `~/.claude/plans/i-have-an-idea-encapsulated-hanrahan.md`

---

## Constraints for this release

Desktop only · **no accounts** · no email · academic track only · solo first.

**UI stack:** Tailwind + shadcn/ui. Components are copied into the repo, so they're owned and restylable rather than a dependency to fight. Accessible primitives come free — and both the hidden-steps drawer and the re-plan diff need real focus and keyboard handling that isn't worth hand-writing.

**Consequence of "no accounts":** team requires identity, so **team and accounts ship together** as the second half of v1.0.0. "Solo then team" still holds — auth simply sits between them.

---

## The one rule that makes solo-first safe

**Build the team-shaped schema. Ship the solo-shaped UI.**

If solo is built with `user_id` on every row and membership is retrofitted later, group-project support becomes a data migration instead of a feature — and migrations against live student work are the most expensive rework there is.

From the very first table:

- A **Project** owns the plan. A user never does.
- A **membership** table exists from day one, even when it always holds exactly one row.
- `StepInstance.claimed_by` exists from day one, even when it's always the only member.
- `project.owner_id` exists and is **nullable** from day one, so accounts later are an UPDATE rather than a migration.
- Any capacity calculation takes a team size from day one, even when that's always `1`.

Solo becomes *the one-member case of a group*, not a separate mode. Cost while solo-only: one extra table, one extra join, two nullable columns. That is the entire price.

## What makes academic different

Not a lighter version of the commercial track. Different constraints, different deliverables, different definition of done.

| | Academic reality |
|---|---|
| Clock | Weeks, fixed deadline, calendar-paced — not hours |
| Judged by | A rubric, and a person who will ask questions |
| Deliverable | Code **plus** report, demo, often a viva — code alone fails |
| Runs on | Frequently the evaluator's machine, sometimes offline |
| Constraints | The brief may mandate a stack, a language, or forbid libraries |
| Success | Submitted on time and working during evaluation — **not** a deployed URL |

### Three mechanics unique to this track

**1. Rubric mapping.** Where a marking rubric exists, steps map to marks. This is academic's equivalent of competition's `criticality` — *"this step is worth 15% of your grade"* is the single most motivating sentence DevCon can show a student, and it makes subtraction obviously correct: work not worth marks is work not worth doing.

**2. Explainability notes — the underserved one.** Students build with AI and then sit a viva where they must defend code they didn't write line by line. That is a real, current, largely unaddressed problem. So each completed step carries a short *"here's what you just built, in terms you can defend"* note — plain-language description, why this approach, the obvious examiner question and how to answer it.

Squarely on-thesis: context-rich, personalised, generated from what they actually built. Feeds both viva prep and the report, and no generic roadmap tool can produce it.

**3. Calendar pacing, not budget allocation.** Competition allocates a minute budget against a countdown. Academic paces against a deadline in weeks, with checkpoints. Falling behind triggers scope-cut advice — the academic analogue of triage mode.

## Scope

Academic track only. Competition and commercial are later releases.

The engine — condition DSL, selection, ordering, `explain`, providers, links — is a prerequisite and carries no solo/team distinction. It is pure and doesn't know how many people are looking at it.

## Profile — academic fields

Beyond the shared profile: `deadline_date` · `deliverables[]` (code | report | demo | viva) · `must_run_locally` · `tech_constraints` (stack mandated by the brief) · `rubric` (optional; unlocks mark mapping) · `group_size`.

## Catalog sketch

Roughly 20–25 steps. Report and viva are first-class work, not afterthoughts.

**Foundation** — read the rubric and map features to marks · confirm constraints from the brief · pick a stack within those constraints · repo and README skeleton

**Core** — data model · one core feature done well · auth *(usually a login screen, not a provider)* · seed data for the demo · second feature only if the calendar allows

**Harden** — **local-run reliability on the evaluator's machine** (this kills more student projects than any other single thing) · error handling on the demo path · input validation, because graders poke at things

**Deliver** — README a grader can follow from a clean machine · project report · architecture diagram · demo script plus recorded backup · viva prep from accumulated explainability notes · submission checklist with deadline buffer

**Group-only** — contribution split and attribution *(many rubrics mark individual contribution)* · module ownership agreed up front

### Anti-steps

| Don't | Because |
|---|---|
| Deploy to production infrastructure | If it only needs to run locally, hosting is unmarked work |
| Add payments | There are no marks for it |
| Also build a mobile app | Scope that reliably sinks student projects |
| Use a stack nobody in the group knows | You have weeks, not a semester, to learn it |
| Leave the report to the last day | It's frequently 30–40% of the grade |
| Over-engineer | Graders reward working, documented, and explainable — not clever |

# Web app

## Persistence without accounts

- A project is identified by a **long random token in the URL**: `/p/[token]`
- Server-side row keyed by that token. No login, no email, no password.
- A cookie holds recently-seen tokens, powering a "your projects" list on the landing page
- **Loud bookmark prompt** the moment the first plan is generated — this link *is* the project

**Known risk, accepted:** a bookmarked URL is the only return path for a 12-week project. It is load-bearing and thin. Accounts and email are the real fix; both are deferred.

## Screens

**`/` — Landing.** The demo *is* the drawer: a real example plan, eight visible steps, "31 hidden" expandable with reasons showing. Don't describe subtraction, show it. One CTA. Recent projects listed from cookie if present.

**`/new` — Start.** No track picker — academic is the only track, so don't ask a question with one answer. Ask the one split that matters: **college project or personal project.**

**`/p/[token]/intake`.** Textarea, four clickable example ideas. Thin-input detection routes to the three guided questions instead of guessing. Optional and high-value: deadline date, deliverables checkboxes, tech constraints from the brief, paste-your-rubric.

**`/p/[token]/confirm`.** Inferred profile as editable chips, low-confidence fields pre-flagged, high-confidence quiet.

**`/p/[token]/stack`.** One recommended provider per capability, alternatives collapsed with `describeFail()` reasons. Respects `tech_constraints` — a mandated stack filters the options rather than being overridden.

**`/p/[token]` — the workspace.** See layout below.

**`/p/[token]/s/[stepId]` — step detail.**

**`/p/[token]/replan`** — diff shown before applying, never after.

**`/p/[token]/deliverables`** — report structure, viva prep, submission checklist.

## Workspace layout — the governing rule

**The plan screen must not look like a 22-item checklist.** If it does, DevCon has rebuilt the thing it exists to replace. One step dominates the view; everything else compresses to single lines.

Single column, no sidebar. Vertical order, top to bottom:

1. **Header** — project name · *week X of Y* · on-track / behind / ahead pill
2. **Progress** — weighted bar, plus *"6 of 22 done · 38% of available marks"* when a rubric exists
3. **Completed** — one collapsed line
4. **NOW** — a single large card: title, personalised why, estimate, mark value, one primary action. The only loud element on the page.
5. **Next up** — three single-line rows, then *"show all 16"*
6. **Don't do these** — anti-steps, visually distinct, reason inline
7. **Hidden drawer** — *"31 steps hidden — here's why"*, each row carrying its failed condition and an "I actually need this" action
8. **Deliverables** — report, viva prep, submission checklist

Exactly one primary button per view. Everything else is secondary or a plain row.

## The return loop

The piece that decides whether a semester-long project survives. On every return to `/p/[token]`:

- *"Welcome back. Week 5 of 12."*
- Pacing banner: on track / behind / ahead
- Active step front and centre, one click to resume

```
expected = (now − started) / (deadline − started)
actual   = completed_weight / total_weight
behind if actual < expected − threshold
```

Weighted by `est_minutes`, **never by step count** — a 6-hour report and a 20-minute README are not one unit each, and counting them equally makes the pacing lie.

### Behind-pace state

When actual trails expected, the NOW card is replaced by a cut recommendation rather than the next task:

> *"You won't finish all 22 steps. At your pace: ~14 hours of work, ~9 hours of calendar. Cut these two and you finish on time."*

Named cuts with mark cost and time saved · **Cut & re-plan** / **Keep everything** · plus a **Protected — do not cut** list covering the report, the evaluator-machine gate, and submission.

Telling a student in week 9 what to abandon is worth more than politely listing work they cannot complete. Ships with v1.0.0, not after.

## Step detail

Back link · title with estimate and mark value · **why this matters** · the generated prompt in a mono block with one **Copy** button · `done_when` as a checklist · notes · **Mark done** / **I'm stuck**.

`Mark done` generates the explainability note and banks it for viva prep — that accumulation *is* the deliverables page, so it must happen at completion time, not be reconstructed later.

### "I'm stuck" — minimal, but in v1.0.0

The parent plan defers the stuck path to M3. It moves forward here in reduced form: **the "it errored" branch only.** Paste the error, get back a debug prompt carrying the step, the profile, the chosen stack, and the `done_when` expectations.

Cost is low — one more generated prompt, reusing machinery that already exists. The reason not to defer: over twelve weeks a stuck student with no recovery path doesn't complain, they just stop coming back. With no accounts and no email, nothing brings them back afterwards.

Deferred: the "result is wrong" and "I don't understand" branches, `common_failures` per step, blocked-state handling. Those need two more authored fields on all ~22 steps, putting catalog work on the critical path for marginal gain.

## Mobile

Desktop only — but **detect a narrow viewport and show a clean "open this on desktop" message** rather than a mangled layout. Students will open the link on a phone first; that's the moment they decide whether this is real. Cheap insurance, not a responsive build.

## Solo — the complete path

Built first. Must stand alone before any group work starts.

Create project → intake → confirm → stack picker → workspace → step detail → calendar pacing → re-plan → explainability notes accumulating toward viva prep and the report.

**Solo-only anti-step:** don't context-switch; finish the step you started.

**Done when** one student goes from an idea to a submitted, working, defensible project without assistance.

## Team — the layer on top

Built second, on the schema that already expects it. Ships with accounts.

- **Members and invite link** — owner plus members, no finer roles
- **Claiming** — `claimed_by` is the whole coordination mechanism. No board, no standup.
- **Shared progress** — completion belongs to the project
- **Parallel assignment**, free from the dependency graph: *"three steps are unblocked, take one each."* Solo gets the same computation inverted: *"nothing starts until step 3."*
- **Owner-only** profile edits and re-plan, so the plan doesn't thrash under the group
- **Polling sync**, ~10s. Not realtime — on a multi-week project, claims change daily.
- **Contribution attribution** — `claimed_by` across completed steps produces the per-person breakdown many rubrics require. Free from data already stored.

**Group-only anti-steps:** don't all edit the same file · don't wait on one person's module to start yours.

**Done when** a four-person group finishes with no duplicated work, no verbal coordination about ownership, and a defensible contribution breakdown.

## Risks specific to this track

1. **The feedback loop is a semester.** A student starting in week 1 tells you nothing until week 12. Mitigation: recruit students already mid-project, and instrument the report and viva steps hardest, since those come last and are where abandonment concentrates.
2. **Rubrics are not standardised.** Mark mapping only works when a rubric is supplied, and formats vary wildly by institution. Treat rubric input as optional enrichment — the track must be fully useful without it.
3. **Academic honesty is a live edge.** DevCon helps a student build and *understand* their project; explainability notes exist precisely to support defensible work. Do not generate report prose that claims to be the student's own writing. Frame the report step as structure and evidence they write from, and say so in the product.
4. **Catalog is 2–3× competition's size.** Report, viva, and documentation steps are all real authoring work. This was the argument for shipping competition first; choosing academic first means accepting that cost deliberately.
5. **No accounts plus no email means no return path but a bookmark.** Over twelve weeks that is thin, and it caps how much the north star can be moved before accounts land.
